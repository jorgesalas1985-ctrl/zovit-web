# SEG-001 — Permisos administrativos y separación de dinero

## Problema revisado
La mejora buscaba comprobar que solo un usuario con intranet_role = super_admin pudiera acceder a funciones financieras administrativas y que los controles se aplicaran en backend, no solo en la interfaz.

## Hallazgos confirmados
- El middleware ya bloqueaba el acceso a /admin/pagos para usuarios sin super_admin.
- Las APIs financieras críticas de payouts, disputes y dashboard admin ya dependían de requireIntranetSuperAdmin(), que valida el rol desde la sesión autenticada y no desde datos del frontend.
- La protección principal estaba en los puntos de entrada de backend, pero no existía un helper compartido para identificar rutas financieras administrativas, lo que dejaba la lógica de autorización dispersa.

## Archivos modificados
- [middleware.ts](middleware.ts)
- [lib/auth/roles.ts](lib/auth/roles.ts)
- [lib/ai/deepseek.test.ts](lib/ai/deepseek.test.ts)

## Explicación de cada cambio
1. Se añadió un helper compartido en [lib/auth/roles.ts](lib/auth/roles.ts) para identificar rutas financieras administrativas como /admin/pagos y /intranet/finanzas.
2. Se ajustó [middleware.ts](middleware.ts) para que esas rutas se traten como exclusivas de super_admin y no queden expuestas a roles como admin, hr_admin, supervisor, worker, client o professional.
3. Se corrigió un problema de tipado en [lib/ai/deepseek.test.ts](lib/ai/deepseek.test.ts) para que las pruebas y la verificación de tipos pudieran ejecutarse correctamente.

## Pruebas ejecutadas
- npm run lint
- npx tsc --noEmit
- npm test

## Resultados
- Lint: completado con advertencias preexistentes, sin errores nuevos introducidos por este cambio.
- Typecheck: completado correctamente.
- Tests existentes: completados correctamente.

## Riesgos pendientes
- El problema de autorización financiera quedó reforzado en los puntos de entrada revisados, pero debe seguir verificándose en producción con el estado real de la base de datos y los permisos aplicados en Supabase.
- La revisión de permisos de tablas y RPC finitas debe seguir validándose con una auditoría de base de datos si se requiere un cierre completo.

## Requiere migración SQL
No, para este ajuste no fue necesaria una migración SQL.

## Estado final
El problema SEG-001 quedó corregido parcialmente en los puntos revisados: los accesos a rutas financieras administrativas están protegidos en middleware y con helpers compartidos, y las APIs financieras principales ya verifican super_admin desde la sesión autenticada. No se detectó una vulnerabilidad clara en los endpoints revisados que dependiera del frontend para decidir permisos.
