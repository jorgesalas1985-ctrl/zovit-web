# SEG-002 — Políticas RLS y seguridad de APIs

## Estado
Estado final: corregido parcialmente con refuerzos aplicados en los puntos sensibles confirmados del código actual.

## Vulnerabilidades confirmadas
- APIs sensibles sin validación robusta de route params o UUIDs antes de consultar datos.
- Endpoints de pagos, requests, verification y worker que podían procesar operaciones con identificadores arbitrarios o sin una validación fuerte de propiedad.
- Exposición de documentos y credenciales sensibles a través de rutas que podían aceptar parámetros no validados o usarse sin un flujo de ownership claro.
- Riesgo de lectura/escritura de tablas sensibles sin un control de ownership claro en el código de backend y SQL de soporte.
- Necesidad de reforzar políticas RLS y seguridad de storage para documentos privados.

## Cambios aplicados
### Backend y validación de APIs
- Se añadieron validaciones de UUID/parametros en rutas sensibles de:
  - app/api/payments/orders/[id]/pay/route.ts
  - app/api/payments/dashboard/client/route.ts
  - app/api/payments/dashboard/professional/route.ts
  - app/api/payments/payouts/route.ts
  - app/api/payments/proposals/route.ts
  - app/api/requests/[id]/cancel/route.ts
  - app/api/requests/[id]/auto-match/route.ts
  - app/api/map/requests/route.ts
  - app/api/admin/verification/[profileId]/route.ts
  - app/api/intranet/verification/[profileId]/route.ts
  - app/api/intranet/workers/ai-validate/route.ts
  - app/api/verification/route.ts
  - app/api/worker/documents/route.ts
  - app/api/verification/certificates/route.ts
  - app/api/verification/certificates/from-worker/route.ts
- Se creó la utilidad de validación [lib/security/validation.ts](../../lib/security/validation.ts) para bloquear IDs no válidos antes de ejecutar consultas.

### SQL y RLS
- Se creó la migración segura [supabase/SEG-002-RLS-SECURITY.sql](../../supabase/SEG-002-RLS-SECURITY.sql) con:
  - habilitación de RLS en tablas sensibles,
  - políticas de ownership para identity_documents, worker_credentials, worker_service_authorizations y worker_review_history,
  - políticas restringidas para roles intranet hr_admin/super_admin,
  - refuerzo del RPC request_payout para usar auth.uid() en lugar de depender de un valor externo del cliente.
